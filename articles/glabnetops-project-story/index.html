From Broadband Operations to GLabNetOps: The Project Story

I started with the Noney BSNL Broadband NMS, then documented smaller tools for network observation and server checks. GLabNetOps is the umbrella I use to connect that work publicly, while keeping the retired production system separate from tools still in development.

The practical problem

The project started with connected work that was hard to see in one place

The public notes for Noney BSNL Broadband NMS describe a rural broadband-franchise setting where work around customer services, network monitoring, infrastructure information, mapping, fault follow-up, and reporting needed to support one another. When those tasks are handled separately, it takes extra effort to connect a service issue with the right network context and the next action.

I wanted related operational work to be easier to follow in one place. The records I have are clearer about the problem and design than about a single starting day, so I’m telling the story through those decisions instead of forcing a neat origin moment.

First form

Noney Broadband NMS: one workspace for service and network operations

The NMS brought together service-facing workflows, network visibility, infrastructure planning, geographic context, and administrative work. The lasting lesson is not that a dashboard solves operations on its own; it is that a shared view is useful only when data ownership, freshness, access control, failure states, and follow-up responsibilities are clear.

The production system is now retired. The public Noney Broadband NMS case study describes the purpose and general design lessons. Its public GitHub repository is a gateway and documentation surface; the private production application and internal configuration are not being republished here.

How the work grew

From a single case to a set of narrower tools

As I documented the work, it made sense to separate broad operational history from smaller tools that solve a more focused problem. GLabNetOps is the working name I use for that direction on this site, rather than the name of one released, connected product.

  • Network Analyzer: an archived 2024 wireless-analysis project and a separate 2026 Linux toolkit are documented as distinct releases. The current case study explains the intended authorized lab scope and limitations.
  • SSH Fleet Doctor: an in-development project exploring SSH-based administration and health checks with a narrow, explicitly authorized scope.
  • Public project pages: each tool now has a case study covering purpose, available setup information, lifecycle status, and safe-use boundaries.
  • Clearer public/private separation: the showcase focuses on documented lessons and public repositories, not private deployment internals or live operational data.

These tools are related by the problems I’m interested in—network operations, system visibility, and practical automation—but I’m not claiming they share a single backend or are integrated into one production service.

Major upgrades

What I want the public record to explain better

The main upgrades in this phase are as much about maintainability and communication as about features. A reader should be able to work out what each project is for, whether it is current, what a safe test looks like, and what is deliberately not shared.

  1. Give each project one permanent case-study URL and a clear lifecycle label.
  2. Document prerequisites and verification rather than giving setup steps without expected results.
  3. Keep the retired NMS as a historical case study instead of implying its production service is live.
  4. Separate the Network Analyzer versions and preserve the older release as history.
  5. Explain the scope and limits of SSH Fleet Doctor without treating an in-development tool as production-ready.
  6. Add public-safe screenshots only after reviewing and redacting them, with captions that explain what the image actually demonstrates.

What I share publicly

Enough to understand the work, not enough to expose private operations

GLab can show the problem, intended workflow, high-level design decisions, development lessons, status, and links to public documentation. It should not publish production source code that is meant to remain private, credentials, access tokens, internal hostnames, network topology, live administrative endpoints, customer records, subscriber details, or unredacted operational screenshots.

The current case study focuses on the problem, high-level design, lifecycle, and lessons rather than reproducing live operational screens. I’ll add diagrams or screenshots only when they are suitable for public release and have been checked for sensitive information.

Current direction

Build, verify, document, then decide what should be public

The next phase is to keep project pages and setup notes current, improve reproducibility where the code is public, and update the case studies when there is a verified change worth recording. I would rather label a limitation clearly than make a roadmap sound like a shipped feature.

Start with the GLabNetOps public overview, or browse the public repositories on GitHub. The repository is the authority for its own current files, release status, and licence.
