From Networking Curiosity to GLabNetOps: The Project Story

GLabNetOps developed from applied network and Wi-Fi analysis, a BCA graduation project and operational software created in a newly established ISP environment. Those experiences informed a network-operations product now developed under GLab Ent.

The early interest

It began with wanting to understand how networks work

The early technical focus was computer networks and Wi-Fi analysis. Early study focused on how networks behave and on analysis tools available in Kali Linux, with the aim of understanding systems and their weaknesses in authorized settings. That curiosity eventually moved beyond using tools.

During the final year of a BCA in Computer Science, Network Analyzer was built as a graduation project. It turned some of networking concepts into a software project that could be organized, tested and improved.

After graduation, work began at a newly established ISP where resources were limited. The day-to-day work brought together customer and service information, network visibility, infrastructure planning, and administrative follow-up. It showed the importance of clear information and practical tools, not only on the network equipment itself.

Broadband operations

Noney Broadband: the ISP’s website and operations workspace

Operational needs at the ISP led to the development of the Noney BSNL Broadband application. It served as the ISP’s main public-facing website and also brought internal work into a shared workspace, including customer records, NetVision, GIS planning, service-related workflows, network visibility, and administration. These areas are connected in practice: a service issue can depend on customer information, network context, location, and a clear next step.

A shared screen is only useful when the data is current, access is controlled, failures are visible, and people know who should follow up. Those are operating requirements, not details a dashboard can solve by itself.

The production system is now retired. The public Noney Broadband NMS case study describes the purpose and general design lessons. Its public GitHub repository is a gateway and documentation surface; the private production application and internal configuration are not being republished here.

How the work grew

From a graduation project and ISP work to focused tools

As the work was documented, it made sense to separate broad operational history from smaller tools that solve a more focused problem. GLabNetOps is the working name for that direction on this site, rather than the name of one released, connected product.

  • Network Analyzer: an archived 2024 wireless-analysis project and a separate 2026 Linux toolkit are documented as distinct releases. The current case study explains the intended authorized lab scope and limitations.
  • SSH Fleet Doctor: an in-development project exploring SSH-based administration and health checks with a narrow, explicitly authorized scope.
  • Public project pages: each tool now has a case study covering purpose, available setup information, lifecycle status, and safe-use boundaries.
  • Clearer public/private separation: the showcase focuses on documented lessons and public repositories, not private deployment internals or live operational data.

These tools are related by the problems I’m interested in—network operations, system visibility, and practical automation—but I’m not claiming they share a single backend or are integrated into one production service.

Major upgrades

What the public project record should explain

This public record is structured to make four things easy to check: what each project does, whether it is current, how to test it safely, and what information is intentionally kept private.

  1. Give each project one permanent case-study URL and a clear lifecycle label.
  2. Document prerequisites and verification rather than giving setup steps without expected results.
  3. Keep the retired NMS as a historical case study instead of implying its production service is live.
  4. Separate the Network Analyzer versions and preserve the older release as history.
  5. Explain the scope and limits of SSH Fleet Doctor without treating an in-development tool as production-ready.
  6. Add public-safe screenshots only after reviewing and redacting them, with captions that explain what the image actually demonstrates.

Public project record

Enough to understand the work, not enough to expose private operations

GLab can show the problem, intended workflow, high-level design decisions, development lessons, status, and links to public documentation. It should not publish production source code that is meant to remain private, credentials, access tokens, internal hostnames, network topology, live administrative endpoints, customer records, subscriber details, or unredacted operational screenshots.

The current case study focuses on the problem, high-level design, lifecycle, and lessons rather than reproducing live operational screens. Diagrams or screenshots will be added only when they are suitable for public release and have been checked for sensitive information.

Current direction

Build, verify, document, then decide what should be public

Next development priorities include updating setup notes, improving reproducibility of public code and revising case studies when verifiable changes occur. Planned work will be labelled clearly and keep it separate from features that are already available.

Start with the GLabNetOps public overview, or browse the public repositories on GitHub. The repository is the authority for its own current files, release status, and licence.
