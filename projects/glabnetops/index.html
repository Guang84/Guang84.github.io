Where it began

From learning how networks work to solving operational problems

The development path began with computer networks and Wi-Fi analysis. Early work explored authorized wireless-observation tools in Kali Linux to understand network behaviour and system security. During the final year of a BCA in Computer Science, Network Analyzer was developed as a graduation project, marking an early transition from studying network tools to building practical software.

After graduation, experience at a newly established ISP with limited resources highlighted practical operational needs. Everyday work made it clear that customer and service records, network status, infrastructure details, and follow-up tasks needed to connect. That experience led to the Noney BSNL Broadband application, which served as the ISP’s main website and also provided administrative and operations tools, including NetVision, GIS planning, and customer records.

The original Noney production environment has since been retired. Its case study remains part of the enterprise project history, while GLabNetOps now connects the documented history with related, separate tools. The records are more reliable about purpose and design than a day-by-day timeline, so this page focuses on what can be established.

Development path

From an early learning project to a documented set of tools

01 · Learning project

Turn network curiosity into a graduation project

Network Analyzer began as a practical way to explore networking and wireless analysis during BCA studies. This project translated that learning into an early software tool. Its 2024 archive and later 2026 toolkit are documented as distinct versions, not as proof that every part of the code or environment remained unchanged.

02 · Operations

Bring connected workflows into one place

The Noney Broadband NMS was designed to put service-related work, network oversight, planning, mapping, and administration in a shared operational view. It is now marked completed and production-retired; this site presents it as a case study, not a live service.

03 · Public boundary

Separate the public record from the private system

The public repository now acts as a gateway and documentation surface. The original production application, internal configuration, and server-side code are not part of this public showcase. Public documentation should explain intent and lessons without exposing access details or operational records.

04 · Focused tools

Keep experiments small and independently understandable

Other GLab projects explore narrower problems: Network Analyzer records an earlier 2024 release and a separate 2026 Linux toolkit, while SSH Fleet Doctor explores remote administration and health checks. These are related interests in network and system operations, not claimed as integrated modules of the retired NMS.

05 · Documentation

Make status, setup, and limits part of the project

The current public presentation emphasizes permanent project pages, reproducible setup guidance where appropriate, explicit lifecycle labels, and a distinction between verified behaviour and intended next steps.

Major changes in direction

What improved as the work developed

  • More connected workflows: the broadband case study documents the goal of linking service work, infrastructure context, and follow-up rather than treating each task as isolated.
  • Clearer lifecycle status: the public record distinguishes a retired production platform, an archived 2024 tool, a 2026 tool release, and a tool still in development.
  • Safer public documentation: project descriptions focus on purpose, boundaries, general architecture, lessons, and public links—not credentials, customer records, internal endpoints, or a private backend.
  • Better repeatability: setup and review guidance asks readers to verify prerequisites, authorization, expected results, and failure behaviour before use.
  • More useful project history: background, development decisions, limitations, and current status live with each case study instead of being left as disconnected repository notes.

Public and private

What this page intentionally does not publish

This is a project overview, not a deployment manual for a private operational environment. It does not publish production source code, credentials, customer or subscriber records, private network topology, live administrative endpoints, tunnel tokens, internal host details, or sensitive configuration. Those details do not belong in a public portfolio.

The current public page focuses on the problem, high-level design, lifecycle, and lessons. Any future screenshots or diagrams will be reviewed for private operational details before publication. See the project template and publishing guide for the optional image-gallery pattern.

Review guide

How to assess the work responsibly

  1. Read each project’s current status before assuming a tool is maintained or operational.
  2. Use the linked public repository for version, licence, and current setup instructions.
  3. For security or networking tools, define an authorized test scope and start in a lab or on systems you administer.
  4. Check actual outputs and current dependencies; do not rely only on an older screenshot or description.
  5. Keep private service details and real customer data out of public issues, prompts, logs, and screenshots.
